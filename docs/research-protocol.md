# Research protocol

## Claims

Every implementation claim must be classified as one of:
- graphemically possible;
- orthographically valid;
- phonotactically possible;
- phonologically possible;
- lexically attested;
- corpus-attested.

These labels are not interchangeable.

## Evidence hierarchy

1. Peer-reviewed phonetic and phonological descriptions.
2. Royal Institute of Thailand standards and publications.
3. Corpus studies.
4. Specialist grammars and theses.
5. Pedagogical sources as secondary corroboration.

The current core evidence includes the Royal Institute, Tingsabadh and Abramson (1993), and corpus-based descriptions of Thai phoneme distribution.

## Reproducibility

Source tables are authoritative inputs. Derived audits are generated by scripts. Manually typed aggregate counts are not authoritative.

## Gold validation

A future corpus release should contain Thai form, morphological boundary, syllable parse, tone, broad IPA, narrow IPA where available, Ukrainian candidate set and adjudicated target. Evaluation should report exact-match, top-k recall, segment-level accuracy and ambiguity rate.


## Source-to-final integrity gate

The project now treats source tables as authoritative inputs and verifies that derived/parser registries agree with them. The generated manifest must pass before CI can pass. This prevents a common failure mode in phonetic software: a source inventory grows while a parser or derived count silently remains on an older subset.

## Orthographic ambiguity policy

If the written form permits multiple phonological analyses that cannot be resolved from the supplied syllable alone, the parser must expose an explicit **analysis-dependent** state and retain the candidate analyses. It must not select vowel length, tone, IPA, or Ukrainian output merely because one lexical item is common. The closed **เ-ิ-** pattern is a regression case: Royal Society evidence documents long **เกิน** versus short **เงิน** under the same structural spelling family. Lexical resolution belongs in a future evidence-bearing lexicon/corpus layer.

## Coda-position validation policy

Final consonant licensing is checked independently of onset inventory membership. If a grapheme is available as an onset but not as a Standard Thai coda, the parser must expose `invalid:coda-not-licensed`; it must not silently discard the grapheme or reinterpret it as an absent coda. This keeps graphemic possibility, positional legality and lexical attestation separate.

## Special orthography policy

Special constructions are represented as explicit, evidence-bearing alternatives when lexical context is required. An implementation must not convert an analysis-dependent construction into a single IPA output merely because a generic parser can produce one.

## Ukrainian target policy

The Ukrainian orthographic layer is a project-specific phonetic target, not an official transliteration standard. Its candidates are deterministic model outputs and require adjudicated Ukrainian data before any probability, preferred form, or normative status is assigned.


## False-cluster validation policy

Sequences such as **จร, สร, ศร, ซร** and lexical **ทร** are not licensed as ordinary true clusters merely from adjacency. Standard Thai descriptions document false-cluster behaviour, including silent ร in established forms such as **จริง**, **สร้าง**, **เศร้า** and **ไซร้**. Because the same spelling patterns can have lexical exceptions or require lexical reading evidence, the syllable-only parser must return **analysis-dependent:special-orthography** and withhold IPA/Ukrainian output rather than force a compositional onset. The browser implementation must consume the same registry and parity fixtures.


## Unicode normalization and layout whitespace

The Thai Python and browser engines normalize to NFC and trim only ASCII layout whitespace (space, tab, CR, LF) at the outer boundary. Other Unicode format/control characters—including U+0085 NEXT LINE, U+200B ZERO WIDTH SPACE and U+202E RIGHT-TO-LEFT OVERRIDE—must remain visible to validation and must not be silently stripped into a valid-looking partial pronunciation. The text tokenizer and `parse_thai` syllable-list API use the same explicit ASCII whitespace set; U+0085 is preserved as unsupported token material, not treated as a layout delimiter. Normalization is not a license to discard unsupported input.


## Mandatory Thai → IPA → Ukrainian architecture invariant

The production contract is a serial pipeline, not two parallel outputs:

`Thai orthography → structural analysis → Thai phonology → typed/inspectable IPA → Ukrainian adaptation from IPA → Ukrainian practical orthography`.

1. The Thai analysis stage determines a source-language reading only to the extent supported by the declared rules and lexical evidence. Its typed phonetic result must expose the IPA representation actually used downstream.
2. IPA is the semantic boundary between the source-language engine and the Ukrainian adapter. It is not merely a debug/audit field. The Ukrainian adapter must not independently reinterpret Thai graphemes, Thai vowel/rime IDs, or Thai coda fields to produce Ukrainian output.
3. The IPA result must preserve the distinctions required by downstream rules, including phonemic versus broad surface IPA, syllable/segment boundaries, vowel length, tone, provenance, and uncertainty. Do not erase a feature before its adaptation policy has been explicitly defined.
4. Ukrainian adaptation must consume the typed IPA result plus only explicitly documented metadata required by the target policy. Any exception must be justified, typed, tested, and must not create a hidden Thai-to-Ukrainian bypass.
5. If source analysis is unsupported or ambiguous and the available evidence cannot choose an IPA reading, withhold the dependent Ukrainian output or return a clearly typed uncertainty. Never fill the gap with an unverified default.

### Required architectural tests

- **Boundary test:** the Ukrainian adapter's public input is the typed IPA result, not Thai orthographic structure.
- **Data-flow test:** for a fixed Thai input, the emitted Ukrainian result is derived from the IPA result that is exposed for that analysis; no second source-grapheme path independently creates it.
- **Fail-closed test:** absent/unsupported/uncertain IPA does not produce a confident Ukrainian transcription.
- **Feature-preservation tests:** tone, vowel length, syllable boundaries, provenance, and uncertainty survive to the boundary and are handled according to explicit Ukrainian adaptation policy.
- **Cross-runtime parity:** Python and browser implementations agree on the same typed IPA result and derived Ukrainian output for shared fixtures.

A passing structural/unit suite verifies software behavior, not the linguistic truth of every IPA result. Keep source-backed lexical evidence, independently adjudicated pronunciation gold, and Ukrainian-native target-form adjudication as separate evidence gates.
